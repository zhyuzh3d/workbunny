# WorkBunny 角色形象与动画包体系：开发计划

状态：首版实现与验收进行中。日期：2026-10-31。

实施进度：通用形象包、只读动作语义目录、分区点击及整包安装、替换和内置版恢复已接入；GLB 数据运行时支持变换、表情形变、材质颜色、弹簧骨骼与双四元数蒙皮。兔兔原始模型、100 个动作和宿主支持的道具特效已迁移为数据包；软体预设当前针对双耳表面结构，不适用于任意拓扑。隔离桌宠测试覆盖全部动作启动及捂脸、拍球、火、雪等代表效果，VRM 播放及包导入、替换、恢复已回归；100 个动作尚未逐条完整视觉验收，后续仍需持续检验实际桌面空间和动画细节。包格式与当前支持范围见《角色形象包-v1.md》。

## 1. 目标与范围

建立一套与具体角色无关的形象运行接口和可分发的数据包规范，让 WorkBunny 能使用由角色、动作、表情、道具、物理和特效组合而成的形象库；现有 VRM/VRMA 继续工作。兔兔及其 100 个动作是首个完整验收案例，而不是接口的硬编码依据。以后用户可以制作、导入、更新和移除符合规范的自定义动画包。

设计目标：

- 一个形象包可以包含一个角色、多种外观和一组动作；动作可组合角色运动、表情、道具、粒子、文字和物理交互。
- 与人形、非人形、无脸、无手脚的角色兼容。耳朵、眼睛、灯泡、球都是资源与能力的实例，不进入公共接口。
- 复用现有 LLM 语义选择与实际播放回执；模型只选择当前形象真实可用的动作，动作数据不成为系统指令。
- 自定义形象的动作、语义与交互映射由形象包固定，用户通过完整形象包升级或替换；现有动作列表管理仅适用于 VRM/VRMA。
- 角色可声明多个随形变运动的交互区域；点击不同部位，从各自预设的反应池随机触发。
- 角色切换和资源更新不破坏现有 VRM、VRMA、角色说明、动作设置与用户数据。
- 首版先提供宿主实现的、可声明组合的运行能力；允许未来增加新的受控运行时，但不要求每个新形象都修改 WorkBunny。

不把首版定义为“能执行任意第三方程序”或“自动支持所有三维动画格式”。数据包可表达什么，取决于宿主实际实现的节点与能力；无法表达的能力必须明确报告，不得悄悄删掉动画内容。将来若需插件代码，应单独设计隔离和权限，不作为普通形象包的能力。

## 2. 当前实现与需要跨越的边界

基于当前源码，而非假定已有通用角色引擎：

1. `src/main/avatars.js` 只扫描 VRM，`src/main/asset-library.js` 仅校验和导入个人 VRM/VRMA；角色以文件名为 key。
2. `src/renderer/app.js` 在模型加载、AnimationMixer、VRM 表情、镜头、头部锚点、人体骨骼命中及坐立切换等环节直接依赖 VRM。
3. `motion-library.js` 当前把全局动作库建在 VRMA 上；`config.js` 按已有动作 key 过滤禁用列表并校验待机；`posture-intent.js` 和 `embodiment.js` 含特定坐立动作 ID。仅在前端插入一个自定义动作列表会使配置、AI、手动播放及回执不一致。
4. 动作链路已具备有价值的约束：`<m>` 可表示分类或具体 ID，主进程选择动作并发 requestId，渲染层确认实际开始，`embodiment` 记录最近动作；手动播放通过同一链路。扩展应保持这些语义。
5. 预览兔兔使用同版本 Three.js r170，但 `bunny.js` 同时负责建场景、UI、相机及循环；模型、动作采样、弹性耳朵、程序化眼睛和场景道具分散在独立脚本，不能把它当作独立 VRMA 列表复制。
6. 桌宠是透明 Electron 窗口；窗口屏幕位置、渲染场景内位移与当前角色的碰撞、气泡、命中区域是不同坐标系。现有窗口和界面需要由宿主统一管理。

## 3. 分层架构与职责

```text
对话 / 工作状态 / 分区点击 / VRMA 动作面板
                ↓ 语义、触发原因、具体动作请求
角色与动作目录 → 能力过滤 → 调度 / 优先级 / 实际播放回执
                ↓ 统一角色运行时接口
┌───────────────────┬───────────────────────────┐
│ VRM 适配器         │ 数据驱动形象运行时          │
│ VRM + VRMA        │ 资源 + 轨道 + 约束 + 特效   │
└───────────────────┴───────────────────────────┘
                ↓
      宿主场景、时钟、相机、桌面窗口、资源管理
```

- **宿主**：唯一拥有 renderer、场景、窗口、事件调度、资源配额及可信运行时注册表。形象包不创建窗口或独立动画循环。
- **形象运行时**：实现加载、播放、逐帧更新、锚点和命中信息等接口；可以是 VRM 适配器，也可以是数据驱动运行时。只有随应用发布的可信宿主代码可注册新运行时或节点。
- **形象包**：声明模型、材质、动画、动作语义和宿主能力参数。普通包是数据；不能自行加载 JS、原生模块或 shader 代码。
- **内部动作目录**：统一提供当前形象可用的动作与语义，供 LLM、状态调度和交互使用；这不是面向用户的动作管理界面。自定义形象动作由包固定；VRM/VRMA 保留现有动作列表管理。

资源依赖为包内相对引用；动作可以引用本包定义的道具和效果。首版一个包对应一个形象；道具作为包内可复用资源，不要求实现跨包资源市场或运行时动态下载。

## 4. 统一运行接口（拟定 v1）

以下是宿主内部契约，名称可在实现时调整；不是赋予导入包执行 JavaScript 的接口。

```ts
interface AvatarRuntime {
  load(context: RuntimeContext, descriptor: AvatarDescriptor): Promise<void>;
  getCapabilities(): AvatarCapabilities;
  getActions(): ActionDescriptor[];
  play(request: PlayRequest): Promise<StartResult>;
  setState(state: CharacterState): void; // idle / listening / thinking / speaking / work 等
  setEmotion(emotion: EmotionRequest | null): void;
  update(dtSeconds: number): void;
  getPresentation(): Presentation;     // 包围范围、气泡锚点、舞台需求
  hitTest(ray: WorldRay): Hit | null;    // 命中的自定义区域及深度
  stop(reason: StopReason): void;
  dispose(): void;
}
```

契约与生命周期：

- `load` 成功后才发布 ready；失败保留或恢复原角色，并返回可诊断错误。使用加载代次取消旧加载的晚到结果。
- `play` 接收稳定动作 ID、requestId、触发原因、循环策略及上下文；明确拒绝未知、禁用、能力缺失或不满足前置条件的动作。不能用待机冒充指定动作。
- 宿主在角色/请求代次仍有效，且动作已实际进入播放后才发送 `started`。动作可发 `finished`、`cancelled`、`failed`；一次请求最多一个终态。兼容当前 `motionStarted`，不把“加载成功”或“发出请求”当成动作已执行。
- `update` 只由宿主时钟驱动；暂停、切后台、跳帧、切换角色时清晰处理时间与模拟状态，不创建第二个 `requestAnimationFrame`。
- `getPresentation` 返回角色本体范围、气泡锚点及保守的动作范围；`hitTest` 返回稳定区域 ID 和命中深度。道具和粒子可有独立可视范围，不默认成为角色可点击区域。无交互区域的形象可明确返回不支持。
- `stop` 停止当前动作、释放其道具与窗口运动并处理终态；`dispose` 清理场景对象、几何体、材质、纹理、事件、计时器和物理状态。资源所有权由宿主或运行时单方明确，避免共用资源被提前释放。
- 切换过程中旧请求、旧粒子和延迟回执不得影响新角色；切换失败、资源缺失、WebGL 丢失时要有清晰回退，而非无限等待。

表现层的状态与动作有通道所有权：例如显式表演独占身体与其声明的眼睛通道，自动眨眼、说话反应和鼠标关注只作用于未占用通道；不支持嘴型的角色声明无嘴型。通道冲突由调度规则处理，不能让每个系统各自覆盖最终姿态。

## 5. 数据包与兼容版本（拟定）

建议使用单文件 `.wbavatar`（ZIP 容器，扩展名和格式名待实现前冻结），导入后以版本目录存储。例：

```text
manifest.json
assets/character.glb
assets/props/ball.glb
assets/textures/...
performances/actions.json
performances/graph.json
interactions/regions.json
```

`manifest.json` 最少包含：格式及版本、包 ID、包版本、角色 ID 和显示信息、作者及资源来源、运行时能力要求、资源清单与内容哈希、固定动作集入口、默认待机、取景及交互区域和反应池入口。动画可以引用一个或多个打包资产，也可以引用宿主内置的声明式节点和效果预设。示意（非最终 JSON Schema）：

```json
{
  "format": "workbunny.avatar-pack",
  "formatVersion": 1,
  "id": "studio_example_character",
  "version": "1.0.0",
  "character": { "id": "main", "name": "示例角色", "model": "assets/character.glb" },
  "requires": { "runtime": "declarative-3d-v1", "features": ["skin", "timeline", "particle-v1"] },
  "actions": "performances/actions.json",
  "graph": "performances/graph.json",
  "interactions": "interactions/regions.json",
  "defaultIdle": "idle_breathe"
}
```

动作记录至少包含包内稳定 ID、名称、描述、语义标签、类别、时长、单次/循环、待机资格、自动触发资格、前置能力、入场/结束状态、空间需求及轨道入口。名称、编号和分类变化不改变 ID；禁止按展示顺序作为持久 ID。

全局身份采用 `(来源, 包ID, 角色ID, 动作ID)` 的结构化元组，宿主生成适配现有 `<m>` 的短 ID 与映射；语义分类 ID 同样隔离。包 ID 和版本不证明作者身份，哈希只校验完整性。用户明确选择已安装形象后，可将新完整包作为升级或替换；同 ID 的其他来源包不能自动覆盖，内置原件也不能被修改。短 ID 的生成必须稳定、可逆查或持久映射，检测碰撞；不能依赖中文显示名、数组下标或不受控路径。

格式大版本不兼容时拒绝并说明最低应用版本；可选字段向后兼容，未知必需能力明确失败。包版本、格式版本和宿主能力版本分别维护。资源引用必须闭合，导出校验生成完整包；不把预览目录的本地绝对路径写进包。

## 6. 动画、道具、物理与特效表达

首版应制定可机器校验的轨道/图结构，而非限定所有角色使用同一套骨骼名称。至少设计并实现以下能力，再以兔兔验证能力是否足够：

- **轨道与混合**：局部/舞台空间的位移、旋转、缩放、材质颜色和标量参数；关键帧、明确插值曲线、事件标记；单次与循环、保持、过渡及动作各自时长。旋转支持完整圈数和轴角，不能把整圈插值抹掉。
- **形变**：标准骨骼蒙皮及权重、形态目标、可声明的参数化形变节点。角色可声明多个眼形或其他表情资源，支持独立节奏；具体实现由宿主节点承载，不要求所有角色有五官。
- **弹性与约束**：通过数据声明骨骼链、根/尖不同刚度、阻尼、角度限制和手势目标；宿主实现固定步长弹簧与必要的平滑蒙皮。首版若要保持兔兔当前双四元数体积效果，应实现并声明对应宿主节点，不能用普通线性蒙皮假装等价。
- **道具与事件**：资源实例的生成、附着锚点、显隐和销毁；球类使用受控的碰撞体、重力、反弹及接触事件。动作受打断、重播时必须完整重置模拟，接触与特效的触发基于真实事件。
- **特效**：宿主粒子、贴图、颜色渐变、纹理、文字、光晕、材质与简单几何预设组合；可参数化雪、火焰、烟、冰、灯光、倒数和文字等效果。资源透明排序、粒子预算和动态文本由宿主管理。
- **动态过程**：通过版本化宿主节点表达随机粒子、噪声、受重力抛物线、接触与弹性反馈；为复现提供随机种子、明确时间单位和更新顺序。跳跃、物理与动作节奏不能只靠截取几帧近似。

一个动作可以组合上述节点，但节点类型、输入输出和参数范围必须有正式 Schema 和版本。每帧顺序至少定义为：推进动作时间与事件 → 根运动 → 表情和主动手势 → 固定步长物理/碰撞 → 更新特效与锚点 → 渲染；具体细节以参考运行时的验收结果冻结。物理步长和最大补算量由宿主限制；长时间暂停恢复不应补算几分钟。

**兔兔迁移要求**：保留连体网格、蒙皮权重、耳朵手势与惯性、眼睛轮廓变形、动作曲线、球交互及全部道具效果。当前部分逻辑是程序代码，不能宣称现成 JSON 直接承载；需要将其转换成通用宿主节点和参数，或对尚不支持的节点明确列出缺口并补齐。第一版先做少量代表动作的对照，完整迁移 100 个动作以实际对照验收为准，不用烘焙成视频替代交互。

## 7. 语义驱动、动作调度与状态

保留现有 `<m>分类ID或具体动作ID</m>`、`<e>` 与 `requestId → started` 链路，扩展为基于活动角色目录：

1. 当前角色 ready 后，向主进程发布经校验的能力和动作清单；目录由主进程确定并与运行时能力交叉校验，LLM、状态、点击及调试调用使用同一快照及版本。自定义形象不接入现有动作列表管理；VRMA 面板继续复用其动作目录。
2. 包中预设语义分类用于 LLM 理解和随机选择，不要求向用户展示动作列表；每个动作另有情绪、意图、使用场景等语义。LLM 提示包含类别和少量与本轮相关的候选，不把 100 条逐条塞进每次提示。
3. 具体动作 ID 精确执行；分类只在当前角色、具备能力、满足状态及自动触发条件的集合中选取。VRMA 另遵循用户的动作禁用设置；自定义包动作集由包决定，不提供逐条禁用。包内自带道具应标记可用；不要把“自带球”错误归类为“缺少外部道具”。
4. 说明文本属于低信任数据，限制长度、作为数据传递，不得覆盖系统提示或向 LLM 索取秘密。没有动作时明确失败，不能声称已经表演。
5. 状态用通用能力及角色自定义状态表示；无坐姿的角色不强制使用 `standing/sitting`。把当前硬编码坐下/站起 ID 改为语义意图与角色能力映射，同时保留现有 VRM 坐立保护。原有 body-state 字段的兼容与升级需同步设计。
6. 定义可中断策略：显式停止/切换角色优先；用户指定动作优先于自动待机；说话、思考与表演的占用按通道解决。动作结束回到该角色自己的待机；自定义包导入时必须有有效的默认待机，VRMA 保留现有待机及禁用校验。
7. 基于真实 `started` 更新近期动作；补充终态与失败诊断，但不得把开始当成已经完整表演。触摸区域由角色声明，并映射到通用交互语义，人体上/下身分区仅适用于有相应区域的角色。

## 8. 分部位点击与随机反应

可以实现，而且区域和反应都由形象包声明。WorkBunny 现有 `interaction.js` 已有按头/上身/下身随机反应及节流，但渲染层通过人形骨骼高度分区，不能直接区分兔兔左右耳。新模式复用“点击 → 合法反应 → 实际播放回执”的宿主链路，不沿用人形专属分区。

### 数据与示例

包中的 `interactions/regions.json` 定义若干**区域**和各自的**反应池**。以下仅示意结构，坐标和动作 ID 不是正式 Schema：

```json
{
  "regions": [
    { "id": "ear_left", "label": "左耳", "hitVolumes": [{ "type": "capsule", "anchor": "ear_left_1", "size": [0.2, 0.6, 0.2] }, { "type": "capsule", "anchor": "ear_left_2", "size": [0.2, 0.6, 0.2] }], "pool": "touch_ear" },
    { "id": "ear_right", "label": "右耳", "hitVolumes": [{ "type": "capsule", "anchor": "ear_right_1", "size": [0.2, 0.6, 0.2] }, { "type": "capsule", "anchor": "ear_right_2", "size": [0.2, 0.6, 0.2] }], "pool": "touch_ear" },
    { "id": "head", "label": "头部", "hitVolumes": [{ "type": "ellipsoid", "anchor": "head", "size": [1, 0.9, 0.9] }], "pool": "touch_head" }
  ],
  "pools": {
    "touch_ear": [{ "action": "ear_twitch", "weight": 2 }, { "action": "shy_hide", "weight": 1 }],
    "touch_head": [{ "action": "happy_bounce", "weight": 2 }, { "action": "curious_tilt", "weight": 1 }]
  }
}
```

示例中具体动作仅用于说明：触碰耳朵可能抖耳、害羞捂脸；触碰头部可能开心跳起或歪头。左右耳既可共用一个反应池，也可分别映射不同动作。实际由制作方在包内固定动作与概率，安装时校验引用；没有对应动作或区域时不虚构反应。可选反应文字、情绪、音效也与动作关联，默认无需调用 LLM；如无可用反应则本次不播放，不假借无关动作冒充。此能力同样适用于翅膀、尾巴、角或非生物角色，不要求必须有耳朵。

### 命中与点击流程

1. 形象制作者声明区域 ID、碰撞代理、绑定的节点/骨骼、局部形状和大小、优先级及反应池。头部可用椭球，弯曲耳朵采用多个绑定耳骨的胶囊或球体近似；代理每帧随骨骼和整体形变更新，不能只用初始静态包围框。对于特殊形变需有明确的宿主支持或标记不支持，不能承诺任意形变都自动精确命中。
2. 指针按实际 viewport 偏移、设备缩放与相机转换成世界射线；先用随动作更新的保守屏幕范围决定窗口是否响应，再通过运行时 `hitTest` 确定具体区域。不同区域重叠先按前后命中深度，再按明确优先级和稳定 ID 处理平局；需验证可见性/遮挡，不能点击穿过前景头部误触背面耳朵。气泡、按钮和输入框优先于角色；特效和道具不默认触发角色反应。
3. 指针按下后沿用现有拖拽阈值：移动超过阈值即为拖动窗口，不再触发点击；取消、失焦和角色切换要释放捕获。点击命中在释放时的区域重新校验，区域或角色已消失则不触发，防止切换中的误操作。范围外保持原有点击穿透。
4. 主进程校验角色及目录版本、区域和反应池，从满足当前状态与能力的候选中按权重随机；多个候选时适度降低上次动作的权重，减少连续重复，但不完全排除，避免两个候选变成机械交替。只有一个候选时允许重复；零权重不选；无有效候选时安静地结束本次点击。选择后的具体动作走既有 `embodiment.perform(..., 'touch')` 和真实 `started` 回执，不由 LLM 临时编造。
5. 使用短时间节流防止连点刷屏；初始可参考现有 900ms，具体值可在实测中调整。沿用当前忙碌/说话/桌面操作保护；本次被抑制就结束，不排队到几秒后突然播放。动画正在播放时按统一优先级和可中断标记决定响应；不因为重复点击破坏动作或重置耳朵物理。语音、气泡、音效遵循现有静音与播放策略，不要求每次点击都说话。

内部使用区域 ID 与动作 ID，不把具体耳骨名写入宿主。点击命中、随机选择、动作开始和结束分别可诊断；随机源可注入以便测试。对于 VRM 角色，保留现有人形点击逻辑，单独回归其表现。

## 9. 桌面空间与呈现

明确三种空间：角色局部、舞台世界、桌面屏幕。根运动与道具在舞台空间计算；气泡与命中投影到窗口坐标；跨桌面移动由宿主窗口协调器控制，包只声明轨迹/空间意图，不直接操作 Electron。

- 每个角色提供基础取景、透明背景、光照预设与锚点；宿主统一协调已有面板让位和尺寸设置，不沿用只针对人形的半身裁切。
- 为动作和道具声明或预计算保守范围，再在实际渲染中验证；跳跃、旋转、雪与烟花不能只依据静态头部包围盒取景。必要时为受控演出临时扩大画布或调整相机，保证动作节奏。
- 需要真正远跑的动作显式声明桌面位移能力；先实现舞台内版本，再单独验收由窗口协调器执行的屏幕级轨迹。处理工作区、多显示器和缩放、屏幕边界、拖拽、面板、打断、窗口关闭及位置保存；物理窗口裁切时不得声称角色可跨越边界。
- 被用户拖拽或新动作打断时停止桌面轨迹，保留实际窗口位置，重置速度与物理跟随，避免旧动画将窗口瞬移回去。屏幕级位置与视觉根运动必须明确分工，避免位移叠加。
- 尊重桌面窗口及点击穿透行为；光、雪等大范围特效默认不扩大可交互范围。

## 10. 用户导入、整包升级与资源生命周期

首版导入格式只接受**声明式数据和受支持的资源**，不运行包内 JS、HTML、WASM、原生库、任意 shader、外部 URL 或 shell 命令；内置特效和节点由应用自身提供。用户可以制作数据包并导入，但不能依靠包夹带自定义代码扩展运行时。若未来需要自定义程序或着色器，需另立安全设计和隔离方案。

导入/升级以**完整形象包**为单位：包含形象、动作集、道具、特效、语义与交互映射；不提供单条动作增删、替换、禁用、重新分类或编辑。用户选择完整包，可新增一个形象，也可明确指定替换现有自定义形象。升级包可以增删或修改动作，但以整包内容为准，旧包不会与新包逐条合并。

替换流程：读取包元信息 → 校验格式、能力、所有资源、动作及区域引用、待机 → 临时目录完整安装并尝试加载 → 成功后原子切换已安装索引与活动版本；失败、取消、进程中断或新版本加载失败恢复旧版本与其索引，当前角色可继续使用。正在播放时先停止旧动作、释放道具与物理，按角色/包代次拒绝旧异步回执，再切换；切换成功才宣告升级完成。崩溃恢复需能区分临时文件、已验证待提交和已提交状态，避免索引指向半包。

内置原包受保护：替换内置自定义角色时，通过用户目录中的完整包作为覆盖版本，保留发行包原件，并可恢复内置版；更新应用不能悄悄覆盖用户选择。个人包可删除，删除当前角色先平滑切离。包 ID、来源与版本作为冲突检测依据，用户明确选择目标；哈希验证内容完整性，不证明来源，不能据此声称同一作者。首版不要求联网自动更新。

验证应覆盖：ZIP 路径穿越、绝对路径、符号链接、重复路径及大小写冲突、压缩炸弹、文件总数和解压大小；资源 MIME/格式、GLB 内外部引用、哈希与引用闭合；模型顶点/骨骼、纹理尺寸、轨道数量与时长、粒子与光源数量、数值 NaN/Infinity 和越界、非法节点及循环依赖。资源上限作为可调整的宿主策略，安装与运行均执行；示例阈值应在真实设备测试后确定。

面向创作者提供格式文档、示例包、离线校验/打包命令和错误定位；基于 GLB 的角色可通过现有建模工具导出模型，动作轨道、节点与语义元数据由配套工具整理。首版是否提供 Blender 导出插件或可视化编辑器由原型验证后决定，不能假设任意 Blender 动画自动支持全部物理与特效。

资源只写入用户数据目录下独立的包目录；安装版本目录和索引采用临时写入、校验、原子切换与失败回滚。读路径应抵御符号链接与校验后替换。角色选择和角色外观说明等已有用户配置与包文件分离；自定义包不保存逐条动作禁用、分类或编辑覆盖。替换后保留仍适用的角色级设置；不存在的旧动作不继续进入 LLM 候选或交互池，近期历史可保留为历史事实。个人数据目录、备份/迁移及卸载逻辑需要把包和索引一并纳入验证。

## 11. 现有代码接入与迁移

建议先通过薄适配层增量落地，避免一次性重写 `app.js`：

- `avatars.js` / `asset-library.js`：形成统一角色目录，识别 `vrm` 与 `avatar-pack` 类型；旧 VRM 文件名 key 保持可解析，现有导入/删除和内置保护保持原行为。
- `motion-library.js` / `config.js`：保留现有 VRMA 动作管理及配置，新增按活动角色取得只读包动作目录的提供器；两者均能提供语义给调度层。包动作不写入 VRMA 的个人动作或 disabled 列表，不引入包动作编辑配置。VRMA 分类、禁用、覆盖及默认待机在切换角色后原样保留；无新包的旧配置不应发生语义变化。
- `embodiment.js` / `posture-intent.js` / `index.js`：以当前角色能力解析意图和过滤候选；回执绑定 avatar、目录版本及请求代次。切换角色时取消旧请求、清除旧能力，拒绝旧回执；维持实际播放记录的真实性。
- `app.js`：把 VRM 特有加载、更新、命中和镜头逐步封装成适配器；新增数据驱动运行时。保留公共 renderer、UI、音频及事件入口，并隔离角色资源和渲染状态。切换后恢复相机、灯光、tone mapping 与场景状态，避免污染另一个角色。
- `panel.js` / 形象及动作面板：VRM 模式保留完整 VRMA 动作面板。选中自定义形象时隐藏或禁用该入口并清楚提示其仅适用于 VRM；不新建自定义动作列表、逐条试听或管理界面。自定义形象在形象入口进行整包导入/替换及版本信息展示；开发测试使用独立的非产品调试工具。
- `resources-manifest.json`、`tools/copy-release-resources.js`、`tools/verify-bundle.cjs`：内置包及必需静态资源登记、哈希校验并纳入发行；个人包只进入用户数据，不被安装覆盖。更新源代码发行与资源说明。

迁移应可重复执行，有版本标记和失败回滚；保留旧配置备份，迁移后核对 VRM 角色、个人文件、动作禁用/分类/覆盖及角色说明。自定义包以包内默认待机为准；切换角色不能过滤或修改原有 VRMA 动作设置。

## 12. 分阶段开发与验收门槛

### 阶段 A：冻结契约与基线

核对当前运行环境、窗口、动作请求和已有测试；编写接口、状态、身份及格式 Schema 草案，准备 VRM 基线和两类不同结构的模拟角色样本。冻结兼容范围与错误码，不变更用户数据。

### 阶段 B：角色适配器与 VRM 回归

接入统一接口，将现有 VRM 行为逐步包起来；原有角色加载、VRMA、动作面板、AI 标签、表情口型、坐立、点击、拖动和位置保持不变。角色切换失败及回执竞态有测试。此阶段不要求兔兔全部迁移。

### 阶段 C：数据驱动运行时与代表动作

实现包校验和基本场景、轨道、表情、弹性骨骼及受控特效节点；用兔兔验证待机、耳朵捂脸、爱心眼、高跳、完整旋转、球碰撞、火/雪/冰等覆盖不同能力的代表动作。对照当前预览检查造型、时间、碰撞和物理反馈，记录尚未支持的节点。

### 阶段 D：完整动作和语义接入

补齐缺失通用节点、迁移并校验兔兔 100 个动作，映射到稳定 ID 和内部语义目录；接入 AI、思考/说话、分区点击与状态冲突管理。开发验收工具可按 ID 精确触发每个动作；产品不提供自定义动作管理列表。自动触发只选适用动作。使用至少第二个非兔结构的测试形象验证协议没有暗含兔子骨骼或眼睛。

### 阶段 E：导入、桌面空间与发行

实现正式用户导入、更新、删除、资源校验和回滚，以及创作者文档、示例包和离线校验/打包工具；完成动态取景、透明窗口及可用的屏幕级轨迹；打包与用户数据迁移纳入验证。若屏幕级运动尚未通过验收，应明确标记该能力不可用，不能用窗口内动画冒充真实跨屏运动。

## 13. 验证矩阵与完成标准

- **协议与资源**：有效包、缺字段、版本不兼容、缺资源、哈希错误、ID 冲突、恶意路径与资源超限均有确定结果；导入中断、更新失败可回滚。
- **播放与状态**：100 个动作可按稳定 ID 单次播放，待机和显式循环正确；开始/结束/取消/失败回执、连续快速切换、重播、切角色、暂停恢复及旧回执不串角色；球的接触、重力及道具销毁符合动作。
- **语义链路**：触摸、LLM 与状态请求始终以同一活动角色目录为准；不支持的具体动作失败，分类不会随机到不兼容项；VRMA 禁用设置仍生效，空闲动作与姿态保护生效。包描述中的指令内容不能改变系统行为。自定义模式不出现 VRMA 动作列表管理功能。
- **点击反应**：左耳、右耳、头部各自的命中区域在摆动、弯曲、遮挡、旋转、窗口移动与缩放时正确；可重复采样验证反应池权重及上次反应降权规则，单候选及空候选安全处理。检查透明穿透、叠层 UI 优先、点击/拖动互斥、频繁点击节流、忙碌保护、切换角色和旧请求。VRM 原有头/上/下身触摸回归。
- **整包升级**：新包可以完整替换动作、资源和交互映射，安装失败、运行加载失败及不同提交阶段中断后恢复旧包；切换时旧特效及回执清理。个人包和内置包覆盖/恢复分别验证；旧动作不泄漏到新目录或被错误触发。
- **视觉与桌面**：在真实 Electron 透明窗口检查角色大小、颜色、表情、耳朵、气泡与命中；覆盖高跳、全旋转、捂脸、冰块、火焰、雪、道具碰撞及快速打断。不同窗口尺寸、屏幕边缘、缩放和多显示器分别验证；录制或采样多个关键帧，不以代码通过代替视觉验收。
- **兼容与数据**：现有内置和个人 VRM/VRMA 的加载、动画、设置、表情、AI 与点击行为回归；新旧配置迁移、应用更新、个人包保留、切回旧版本的限制有明确结果。
- **性能与稳定性**：在目标设备实际测量启动时间、帧时间、GPU/内存和持续运行资源占用；反复切换及播放检查泄漏。基线、设备、数量和可接受阈值在阶段 A 确定，不能事先虚报性能达标。
- **打包与真实环境**：验证发布包包含内置运行时与资源、哈希一致、用户数据保留，覆盖干净启动。真实桌面视觉、多显示器和设备性能分别记录；无真实验证不称已通过。

## 14. 实施前需冻结的选择

1. 首版 `.wbavatar` 格式的 Schema、版本号和扩展名，以及 GLB、纹理、轨道与事件的精确子集。
2. 哪些通用节点足以无损承载兔兔的程序化眼睛、双四元数耳朵和实时球碰撞；不支持项的错误与后续扩展方式。
3. 动作优先级、跨动作过渡、屏幕级位移的触发条件及用户设置；特别是用户拖动时的行为。
4. 默认动作 ID、分区碰撞代理与反应池格式；已有 VRMA 分类/禁用设置在切换模式时如何原样保留。
5. 整包更新的版本/冲突处理、内置形象覆盖和失败恢复策略。
6. 目标设备和视觉验收方法。所有数量、性能阈值及工期应在代表动作原型完成后依据实测收敛。
