# 统一任务编排重构计划

日期：2026-11-03。状态：设计与迁移计划，**尚未按本文实施或验收**。以当前工作区 `package.json` 的 0.24.6 源码为核对基线；当前工作区可能同时包含尚未提交的改动。本文不表示这些改动已经安装或经过真实环境验收。UI、记忆和任务三大系统的职责及上下文组装器见[整体架构设计](整体架构设计.md)。

目标是在现有任务运行时上，统一任务内部的条件、循环、事件和业务动作，使 Bunny 在授权内主动思考、灵活行动并解决问题，同时保证并发、恢复、升级和外部写入有清晰边界。经验是服务任务的记忆，工具是经验引用的资源，软件技能可作为按分类或标签组织的一组经验；Bunny 能在实践中检索、组合、验证和改进。架构应支持 Bunny 针对陌生任务选择方法、观察效果并自主恢复。完整产品方向见[产品目标与智能体设计原则](产品目标与智能体设计原则.md)。衡量标准是可靠、及时地完成原任务，而非建立复杂的通用工作流平台。

## 1. 核心模型与职责

```text
主人交办 → 任务：目标、授权、对象、期限、进度与回执
                  ↓
             统一编排器：状态、唤醒、依赖、取消、恢复、资源
                  ↓
    顺序 / 条件 / 循环 / 等待事件或时间 → 业务动作实例
                  ↑                              ↓
       画面、消息、计时、工作进度等事件     观察 → 语义判断和程序 → 操作 → 核验
                                                 ↓
                                      已注册的工具和应用适配器
```

- **编排器**是任务的唯一状态和生命周期协调者，负责准入、持久化、事件分发、依赖、唤醒、取消、恢复与资源仲裁。应用适配器仍负责各自的观察、定位、输入和证明；WorkBuddy 负责其被委派工作的执行，Bunny 跟进与验收。这里的“唯一”指一套任务协调语义，不要求强行合并前台普通对话、WorkBuddy 内部运行器或系统通知。
- **上下文组装器**是任务系统连接记忆系统的核心能力：依据目标、软件、执行阶段、触发事件和模型容量，灵活选择个人理解、历史记忆、相关经验及其引用资源、环境与结果等内容模块及参数，按需提供经验概要或完整信息；基础对话可以调用轻量组装接口，但不因此创建业务任务。具体设计见[整体架构](整体架构设计.md)和[记忆演进设计](经验与工具的记忆演进设计.md)。
- **任务**是主人目标与授权的边界；可一次完成，也可持续监测。现有任务 ID、来源、权限、对象、名额、暂停/继续/停止和完成条件保持不变。按现行规则，最多启动 5 个业务任务，超额任务需手动启动；不得借重构改变这一产品规则。
- **业务动作定义与实例**：定义说明目标、输入、可能的副作用、核验与冲突策略；实例绑定任务、触发事件和对象，具有自己的生命周期、检查点与结果。一次“回复 Alice”“提交工作”各是一项业务动作，可以包含多次模型调用与多个程序步骤。现有的截图、点击、发送等**工具调用**是其中步骤；复用当前工具注册、授权和回执机制，不把每次模型请求误称为完整业务动作。
- **条件、事件、等待与循环**：条件依据明确证据返回成立、不成立或未知；未知不等于不成立。事件是需要处理的事实，画面变化只是触发观察的信号。循环和等待负责按条件、事件或定时唤醒节点，技能提供业务经验而不是限制思考和路径。先支持顺序、条件、循环和事件/计时等待，表达当前真实需求即可，不引入通用 DAG、分布式队列、脚本语言或新的工作流服务。
- **LLM 与程序**：模型根据任务和观察选择方法、进行语义判断并分析失败；程序保障状态、身份权限、时序、参数、真实副作用及回执。确定性操作可直接推进，不必每次都请求模型；遇到不熟悉的问题应能重新观察、推理并组合允许的工具。外部消息、截图、网页及工作结果都是数据，不能变更目标或增加授权。

有一个需要特别保留的现状：[`conversation.transcribe`](../src/main/conversation-tools.js) 在工具契约中是 `read`，但会通过键鼠打开微信菜单并请求转写。数据读写类型不能等同于是否操作 GUI；重构必须把两者分开处理，否则只读动作可能绕过租约或在异常后盲目重复点击。

当前 [`ToolRegistry.check`](../src/main/agent-tools.js) 把 `skill.tools` 清单当作硬门槛。重构须将技能提供的方法建议与平台授权分离：在主人已授权的任务、对象和应用方法边界内，向 Bunny 提供适用的已注册工具；每个调用仍校验实际能力、参数、资源与副作用。不能用技能未列出某工具就排除已授权的替代方案，也不能借此扩大任务授权。按技能逐项迁移并验收，当前清单在兼容期内继续生效。

### 优先处理：当前 Alice 卡住的已确认机制缺陷

2026-11-03 的任务界面显示“发送结果待确认”，具体原因为“目标窗口改变，已暂停”，一条动态仍在队列。安装版与工作区的相关源码经哈希比对一致；现有界面不能证明当时究竟是前台应用、窗口身份还是窗口几何发生变化，也不能单凭该状态断言消息实际已发送或未发送。

隔离夹具复现了同样的错误链：[`desktop-service.js`](../src/main/desktop-service.js) 先记录 `type` 意图、点击输入框，随后窗口核查失败；实际没有发出文字或发送指令，但这条 `intent` 被 [`agent-service.js`](../src/main/agent-service.js) 当作可能存在草稿，最终 [`agent-runtime.js`](../src/main/agent-runtime.js) 将整个写入标为结果不明。对应的恢复路径在缺少“已输入草稿”或提交前画面时，会在重新观察之前直接返回，导致 Bunny 无法主动核对并继续。此复现证明存在该缺陷；是否正是当前任务发生的具体步骤仍待任务证据确认。

优先修复方向：分别记录**聚焦、文字输入实际发令、提交实际发令及其结果**；有证据确认文字未发令时重新定位并继续，草稿状态不明时自行重新观察，确认是本次草稿后继续，确认空白且没有在途输入时再安全重试。提交可能发生时自行寻找发送前后画面、同一会话新气泡和输入框证据；不能确认时保留待核对，不重复发送。增加每个阶段的脱敏原因与耗时；避免把界面位置变化直接升级为永久等待或“可能已发送”。

当前桌面执行在整个操作循环内持有 GUI 租约，每一步可能重新截图并等待视觉模型；输入和提交前还可能分别强制视觉观察。重构应把 GUI 占用缩到必要的操作窗口，复用有效观察、仅在相关条件变化时重新识别，并用反馈驱动等待；避免把慢模型和无关像素变化变成整段任务的停顿。

## 3. 事件和动作如何推进

### 3.1 观察、触发和执行分离

监听可以是一个按期唤醒的检查，也可以由外部事件唤醒；检查对象可为画面区域、文件、接口或其他数据。检查本身执行必要的程序或语义判断，区域失效时主动重新定位；多个监听可共享调度和观察资源，不为每次采样都启动 LLM。

1. 观察器负责取得可靠证据，按来源、对象和消息顺序形成事件；**先持久化事件及其游标，再安排动作**。事件含稳定 ID、任务 ID、来源、对象、观察时间/序号和必要的证据引用；不把截图或消息原文放进普通日志。
2. 事件在明确完成、按主人规则处置或转入可追踪的待核对状态之前不得被静默丢弃。重复观察同一条消息不能重复触发；同一联系人后来再次发送相同文字仍是新事件，不能仅用正文去重。游标推进与事件入队必须原子提交；提交失败保留原游标，恢复后可重新观察。一个动作可以关联一批事件；替换动作时以一次持久化转移未完成事件的归属及新旧动作状态，不能先消费事件再指望新动作创建成功。
3. 后续采样“没有变化”只说明该采样没有发现新的变化，不取消已经记录的事件或正在进行的动作。模型调度有延迟时，即使下一帧静止，返回的决策仍按原事件继续执行。
4. 如果决策依赖当前画面或目标，执行前可独立抓取新画面，核对窗口、对象、权限、目标控件与必要前提；条件仍成立就执行，相关条件确实改变时保留原事件，重新观察并调整动作。不得用“画面是否变化”单一布尔值代替业务前提判断，也不能只因时间过去而丢弃动作。
5. Bunny 结合目标、当前证据与技能经验决定是否需要模型、如何执行和如何核验；可证明未执行的临时失败主动重新定位、调整方法并继续，未确认的外部写入主动核对。只有证据支持的回执才推进后续依赖。

### 3.2 独立生命周期、并发与停止

- 每个业务动作实例至少记录：任务及节点/动作 ID、触发事件及目标、授权和目标版本、阶段、重试预算、已确认步骤、外部写入意图和核验结果。运行中的控制器属于该实例；实例可恢复，不能仅依赖内存 Promise。不同任务的动作互不取消；同一任务内无依赖且冲突策略允许的动作也可各自异步推进，观察可与动作及 LLM 调度并行；有依赖的动作按顺序推进。
- 任务状态、事件与动作检查点通过按任务串行的提交入口统一修改，必要时用版本比较拒绝过期写入；提交入口基于最新状态应用变更并持久化，不能让观察器和执行器各持旧快照覆盖彼此。截图、模型和远端等待不能占用状态提交锁。共享 GUI 键鼠继续由同一个租约串行；只读观察并行不意味着可以抢焦点或在他人输入时滚动。每次获取租约后按操作风险核对当前目标。模型和采样并发设有界预算和公平排队，避免单个联系人或长任务饿死其他任务。
- 版本分工必须明确：任务**状态版本**仅用于提交冲突检测；动作绑定的**目标/授权代次**和所属对象的**事件版本**才用于判断结果是否仍有效。任务停止、实质目标/授权变化或同作用域新事件替换时递增相应代次；普通状态落盘、检查周期变化和其他对象事件不能使动作过期。即使模型或工具忽略取消并晚返回，结果也必须在进入下一步骤前核对有效性；已发生或不确定的外部写入仍要保存回执并核对。外部副作用开始前，在统一提交入口再次确认代次和事件归属并记录保护阶段；只有持有有效 GUI 租约且重新确认目标后才可输入。
- 停止/替换与发出副作用之间要有同一任务的短暂发令屏障：先完成状态和意图持久化，再在屏障内最后检查有效性并开始发出操作；若停止或替换先取得屏障，就不发出旧操作。若发令先发生，停止只能阻止后续步骤，并将该操作视为在途或结果未知。屏障不等待模型、截图或外部回执；崩溃时无法证明是否发令的操作按未知处理。这样不能撤销已发送的输入，但能明确停止与发令的先后。
- 默认冲突策略是**独立**。只有动作明示支持、作用域和条件都吻合的新事件才能替换旧动作。自动会话回复的作用域为同一任务、场景、应用及已确认的同一联系人；不同联系人、其他任务、普通单次发送、成果交付和工作提交互不替换。目标尚不确定时先核实，不据此取消。
- 两个任务若都监听同一联系人，应在接单时检测重叠；主人意图是修改原任务且目标、授权匹配时优先调整原任务，明确交办两个独立任务时不擅自合并。不能可靠区分或协调时保留冲突状态并明确说明，不能悄悄停止已有任务。对已存在的重叠任务，复用同一场景事件证据，并在实际发送前协调该外部会话的写入：只有能证明两个动作对应同一来信且任务要求可由同一回执满足，才共享处理结果；否则分别保留、重新判断，不只凭消息正文去重，也不以跨任务取消代替协调。
- 主人暂停、停止、取消任务，或来源/授权失效时，向该任务全部子动作传播停止并阻止新的副作用；调度周期等非目标性修改不应中断正在执行的动作。目标、对象或授权发生实质变化时按明确规则取消或重新规划，而不是依赖任意画面变化。
- 停止是协作式的：若外部提交已发生或无法确定，停止后仍须保存可能迟到的回执或做只读核对，不能声称已撤销外部效果，也不能继续下一业务动作。界面应区分正在停止、已停止和结果待核对。
- 动作可声明自己的超时、恢复和重试策略；等待过久应记录真实阶段、分析原因、调整方法或提示，不能仅凭计时推断外部写入没有发生。预算防止无效循环，达到预算不等于放弃原目标；依据进展换方法、合理退避或说明确实无法自行解决的原因。父任务的有效期和明确停止优先，超时后的恢复遵守相同的副作用边界。

### 3.3 外部写入及异常修复

动作按实际协议记录准备、可能产生草稿/其他副作用、提交、核验和终态；各适配器声明真实的不可逆边界。发出输入或提交前先持久化意图，持久化失败不得输入；有确切未执行证据才可重试。已确认的同一操作复用原回执，同一 ID 不得换参数；因新消息重新生成且参数改变时使用新的动作版本和操作 ID，并保留原实例状态。提交结果不明时只读核对；仍无法判断则保留待处理，禁止重发或假定失败。无法保证外部系统严格恰好执行一次，只能利用本地标识、证据和核对降低重复风险。

工具契约分别描述数据效果、是否操作 GUI、目标范围和恢复方式。语音转写等“读取内容但要点击界面”的工具仍必须取得 GUI 租约并核实位置；中断后先观察对应语音是否已出现转写或仍在处理中，再决定是否安全重试，不能因为标记为 `read` 就直接重复点击。普通纯观察可使用其自身的安全重试策略。

沿用[任务异常自我修复设计](2026-11-03-任务异常自我修复设计.md)中已经实现的请求级修复，并扩展为动作级自主恢复：先使用已有局部修复，必要时让模型根据最少必要上下文分析错误、提出可行替代方法，结合观察自主核对并从原动作检查点继续。请求参数调整仍遵守受限契约；不得擅改目标、来源、授权或绕过正式 schema 校验。未知写入先主动核对，取消/身份变化后不靠修复继续执行；预算和节奏用于防止无进展空转，不能替代诊断和可行的恢复。

## 4. 微信照看实例

1. 定时或变化检测发现目标联系人未读标记时，及时打开指定会话；必要时滚动联系人列表寻找。若会话已经打开，则检查消息区域的新来信，不依赖红点。红点用于发现和定位，发送前仍须核实会话标题、确实来自对方的消息和必要内容，避免回复错误对象或把历史消息当新消息。
2. 主人已交办“照看并回复”时，经过确认的新消息默认产生回复动作，不再让模型以笼统的“是否值得回复”反复否决。只按主人明确的特殊规则处置，如广告忽略；证据不足时主动重新观察/定位，无法安全确认时保留并说明，不伪造回复完成。
3. 连续多条消息先持久化并按顺序合并，立即着手生成，不为等待静默人为延迟。生成或等待键鼠期间持续观察：**确认同一联系人出现更新消息**且旧回复尚未开始产生外部副作用时，取消旧准备动作、保留事件并基于合并后的消息重新生成。其他联系人消息只排队，不打断原回复。对不同任务和联系人公平推进。
4. 旧回复已有草稿时在安全检查点停止提交；仅当能可靠证明草稿由本动作产生且可安全处理时才按明确策略处理，否则保留草稿并待核对。提交已开始或结果未知时不得当作未发送，先核验或进入结果待确认；新消息排队，依据确认结果继续。持续高速来信可能反复使旧回复过期，应优先合并、缩短必要调度路径并显示积压，不能为消除饥饿而悄悄发送已知过期内容。
5. 对语音消息，视觉定位对应的对方语音，使用微信可见菜单请求“转文字”，随后持续检查对应转写结果；识别完成并确认对应消息后纳入回复上下文。识别延迟/失败时保留事件、按规则重试或提示，不把未识别语音编造成文字。
6. 所有微信内容读取和操作只使用外部截图、视觉/OCR 与通用键鼠；禁止微信 UI 树、内部 API、数据库、插件和协议。窗口失效、身份变化或证据不足时重新定位或按现有机制等待核对，不能盲点、重登或冒充发送成功。

## 5. 状态、兼容与资源

- 以现有 `AgentRuntime`、`SkillRegistry`、`ToolRegistry` 和加密账本为基础扩展，不另建平行任务平台。运行时提供按任务提交变更、挂接/唤醒事件、创建/恢复动作和传播停止的内部接口；技能提供动作的推荐方法与核验经验，Bunny 可在授权内选择和调整；工具继续提供参数、权限、对象和回执校验。具体 API 命名以实现为准。
- 为自主解决问题提供统一能力：观察和操作、模型与上下文、阶段/错误/回执、主动核验，以及经验和工具的创建、改进、验证、复用与回退。成功与失败都可触发经验提炼；允许在已有授权内创建或更新任务工具并按影响自主试用，推测与实际结果分别记录。已有来源、遗忘和场景权限继续生效，不能用经验自动扩大能力。先复用现有 `AgentLearning` 和工具执行机制，按实际缺口扩展，不新建独立的自我进化平台。
- 最小持久化模型：任务保留现有目标、授权、`inbox`、`operations` 和调度信息；事件记录来源、对象、顺序、处理状态与关联动作；动作记录 ID、目标范围、关联事件、任务/对象版本、执行状态、恢复检查点及关联工具操作。动作状态与外部写入状态分开：例如动作已停止，但某次提交仍可能是“结果待核对”。字段和表示可复用现有结构，不要求新增表或照搬术语。
- 逐步接入时，将 `pendingScreenMatch` 映射到可恢复事件，将 `pendingDecision` 关联其业务动作和触发证据，会话的游标/事件与工作委派的任务绑定继续由原技能维护；新旧路径只在安全边界切换。工具调用仍可有内部取消信号，但业务动作和工具操作不得各自独立决定事件已完成。
- 优先扩展现有加密任务记录，保存最小的动作实例、事件引用、检查点与回执；不复制截图、完整消息或新建第二套账本。来源删除、场景隔离、资料库锁、身份和能力校验沿用现有机制。是否必须变更 `bunny.task/v2` 由实现时的兼容性验证决定，不预设 schema 版本号。
- 每次状态提交必须避免观察器与执行器用旧快照相互覆盖；事件入队、游标和关联状态一致持久化。崩溃可在每个阶段重启，按记录恢复尚未执行的工作；提交结果不明先核对，不从头重放。待处理事件、周期、剩余时限、来源及授权不能因升级消失。
- 旧任务优先继续由创建它的既有执行路径处理；仅在无活动动作、无未决副作用且状态可完整映射的安全检查点迁入新路径。遇到未知写入、旧草稿或不支持的状态继续旧路径核对，不能用新实现重新派发。一次任务同一事件的外部写入只能由一个路径拥有；影子运行仅做只读观察和差异记录，不发起发送、提交、报告或其他副作用。
- 升级前验证旧记录读取、新旧数据兼容和受支持的加密备份/恢复；回退版本必须能安全识别升级后记录，做不到时先提供经测试的兼容读取或降级转换，不得直接回滚应用并丢弃新状态。备份遵循原有密钥、授权、删除及保留策略，不另存明文截图或消息。
- 延续共享场景观察与窗口有效时的局部采集、静止画面跳过不必要识别；周期性核对及已触发动作不受此优化影响。避免每个动作或联系人各建一套高频截图与模型循环。等待 LLM、计时和 WorkBuddy 时不占 GUI 租约；资源限制不得悄悄清除待处理事件。
- 在本机记录脱敏的任务/动作 ID、阶段、排队与等待时长、重试和取消原因、结果类别；指标不包含正文、截图、凭据。任务界面展示当前动作、最后有效观察、积压和真实等待原因；通知按事件和阶段去重，不把停止、失败或未知状态显示成完成。

## 6. 分阶段实施与交付门槛

每一阶段先在隔离数据和可重复夹具上通过，保留旧路径和回退开关；不同时运行两条会写入外部系统的路径。先收集基线，按阶段小步提交与验收，失败则停在当前阶段处理，不以扩大重试掩盖故障。

| 阶段 | 交付内容 | 进入下一阶段的门槛 |
| --- | --- | --- |
| 0. 基线 | 梳理真实入口与现有调用者，固定任务、事件、操作和恢复样本；测量延迟、资源及当前缺陷；标明源码、已安装版本和实测环境。 | 现有离线回归可复现；列出真实验收缺口和基准，记录正在运行任务的兼容范围。 |
| 1. 核心机制 | 优先修复输入前窗口变化造成的错误未知状态与无法主动核查问题；在现有运行时内加入业务动作实例、统一事件/状态提交、取消原因、版本检查和恢复；工具回执继续使用现有机制。 | 区分聚焦、输入与提交的故障注入通过；并发覆盖、取消、重启和未知写入正确，旧任务与现有工具回归通过。 |
| 1.5 上下文组装 | 抽取可组合的内容模块与参数选择接口，先接入一类任务，并为基础对话保留轻量调用及兼容路径；逐步支持按软件和用途检索经验、按需提供概要或完整信息。 | 不同任务阶段可选择相关记忆、经验、工具和预算；标签无命中时可检索相邻经验或使用通用工具；上下文溢出可重组而保留当前目标、事件和必要证据；普通对话不创建长期任务。 |
| 2. 观察与条件 | 将画面条件、计时和会话观察接入同一事件契约，保留应用专属识别；引入只读影子对照。 | 触发后静止、延迟模型、游标入队原子性、重复消息及丢帧恢复通过；影子路径无外部副作用且无双重通知。 |
| 3. 会话与语音 | 将自动回复作为首个完整业务动作迁移，接入持续观察、同目标替换、草稿/提交保护和语音等待；先新建隔离任务，后逐步开放。 | 同/不同联系人并发、连续多条、静止画面、语音、草稿及不确定发送通过；真实微信按授权范围独立验收，不能用模拟代替。 |
| 4. 工作与组合操作 | 迁移 WorkBuddy 提交/跟进/交付及通用软件组合动作；在授权范围内开放适用的通用工具，并接入经验和工具的自主创建、验证、复用、改进与回退。梳理现有监督、回报和其他入口。 | 保留原工作绑定和结果，故障恢复不重复委派、交付或汇报；陌生布局与替代方法能自主解决，工具创建和复用不扩大授权，历史/在途任务兼容与隔离实测通过。 |
| 5. 收敛与发布 | 在新旧任务完成兼容期后移除确认无调用方的重复调度逻辑，保留必要适配器；完成文档、打包、安装、回退及长期观察。 | 所有门槛通过；升级和回滚演练不丢事件、授权、回执或未决操作；真实证据和未覆盖项单独记录。 |

切换粒度以技能/新任务为主；在途任务不强制中断迁移。功能开关关闭后，仍须保证已由新路径创建的任务能被安全读取和处理；不能把“关闭开关”当成已经验证的数据回滚。后续实施需要安装时沿用现有签名与安装流程，并按当时版本只增加第三位版本号；本文不进行版本升级或安装。

## 7. 验收矩阵

| 要求 | 必须验证的场景 |
| --- | --- |
| 已触发动作不被静止画面中断 | 构造“变化触发 → LLM 等待 → 新采样无变化 → LLM 返回”，验证动作执行；另测真正前提变化后的独立复核和重规划。 |
| 同目标新消息与独立并发 | 同任务同联系人、同任务不同联系人、不同任务相同/不同联系人；连续多条、重复正文、新消息在 LLM/草稿/提交各阶段到达；迟到的旧模型结果被版本检查拦截，没有隐式跨作用域取消。重叠任务对同一外部来信不能无依据地重复回复或合并回执。 |
| 取消和修改 | 父任务暂停/停止/授权失效时子动作停止；仅改周期不取消；终止与写入回执同时到达时保存真实结果，不执行后续步骤。 |
| 持久化与故障 | 入队和游标提交失败、旧快照并发写入、每个检查点崩溃重启、名额耗尽、队列满、资料库锁定和身份变化；无丢事件、重复外发或越权。 |
| 写入安全与恢复 | 未分发失败可重试；草稿、提交前后及网络超时分别处理；已确认复用回执，结果不明只读核对；同 ID 异参拒绝。 |
| 会话与语音 | 有红点/会话已打开、滚动找人、语音转写延迟和失败、外来内容注入、消息超出可见区域；转写点击前后中断时先重新观察，不重复盲点；明确标记无法确认的部分。 |
| 自我修复 | 上下文不足、结构输出错误、诊断超时、预算耗尽和修复时取消；原事件/目标/权限保留，未知写入不重发。 |
| 自主行动与经验演进 | 无现成技能配方、界面布局改变、首选工具失败时，结合允许的工具主动观察、探索替代方案并核验；在已授权的隔离任务中创建或改进工具、试用并记录结果，后续可检索复用，失效后能修正或回退。 |
| 灵活上下文 | 基础对话、普通任务、操作和错误诊断按需选择不同记忆模块、经验、工具和参数；来源变化可重新检索，模型延迟或预算调整不丢当前目标与已触发事件。 |
| WorkBuddy 与既有用户体验 | 原工作会话绑定、进度、验收、交付与通知去重；待启动仍需手动启动；任务卡片状态和停止语义真实。 |
| 升级和回退 | 从代表性的旧版加密数据、运行中任务和未决操作升级；模拟崩溃和回退，验证状态、授权、数据删除边界及结果一致。 |

自动回归以 `npm test` 和针对性测试为基础，涉及桌面、真实账号、重启和长时间运行的检查按 [`test/README.md`](../test/README.md) 单独执行。离线夹具、只读影子对照、真实微信/WorkBuddy 往返及长期运行是不同证据，分别记录通过与未覆盖，不能互相代替。真实外发验收仅在已有明确任务授权和可控目标范围内进行。

## 8. 性能与稳定性验收

阶段 0 在相同机器、账号、任务、观察周期和模型条件下记录：消息确认到动作启动/提交/核验的 p50、p95、p99；队列等待、LLM 等待、GUI 租约等待和吞吐量；空闲和活跃时 CPU/内存、截图/OCR/模型请求次数，以及模型 token 与失败/重试次数。重构后用同一场景对比，并记录样本数和波动；从基线与产品目标共同确定数值阈值，不预先捏造“提速比例”。阈值须在相应实现优化和验收前确定；结果在测量误差内只能称为持平，不能宣传为提速。

产品体验目标：网络和模型服务正常、目标会话可访问且无需等待主人操作的常见文本回复，从新消息确认到发送结果核验应力争在几十秒内完成。阶段 0 测定分位数并设定可复现的验收阈值；该目标用于定位和消除延迟，不作为到点中止动作的硬超时。

确定性夹具必须证明已可靠采集的事件不丢失、同一已确认外部写入不重复、其他对象不取消当前动作、任务停止后不再发起新副作用；时延和资源不得出现超出既定阈值的退化。完成整体重构前，至少一个事先选定的主要热路径要在基准场景中取得超出测量波动的改善；如果没有，记录结果并继续优化，不能宣称性能目标已完成。真实环境单列网络、模型和微信界面限制，长时间测试验证资源稳定及恢复，任何一次结果未知都按待核对统计，不能算成功。指标发现回归先定位并修复，达到明确门槛后才扩大接入。
