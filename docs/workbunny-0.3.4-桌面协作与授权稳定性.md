# workbunny 0.3.4：桌面协作与授权稳定性

2026-10-25。延续 [concept.md](../concept.md) 与 [0.3.1 验收](workbunny-0.3.1-迭代验收.md)。本轮以真实安装包验证钥匙解锁、窗口截图、WorkBuddy 派发和微信视觉收发。

## 重复钥匙串弹窗的根因与处理

只读检查指定的 `workbunny Safe Storage` 项目，确认登录钥匙串处于解锁状态，ACL 没有要求每次重新输入密码；受信应用是 workbunny，但其 partition 列表记录的是主应用的多个 `cdhash`。主应用资源更新会改变 CodeDirectory 哈希，因此固定应用名、路径和自签名证书仍不足以避免每次重打包后重新授权。[Electron 的签名边界](https://www.electronjs.org/docs/latest/api/safe-storage/)、[Apple 对 CodeDirectory 哈希的说明](https://developer.apple.com/documentation/technotes/tn3126-inside-code-signing-hashes)。

新增独立的 `workbunny-keychain.app`，普通前端更新保持其编译产物、Info.plist 和签名身份一致。Keychain ACL 只信任这个辅助程序。辅助程序从内核读取真实父进程信息，并验证父进程具有相同证书、预期 identifier、有效签名和同一个安装包中的可执行路径；复制辅助程序并搭配未签名的假父进程不能解钥。旧的 Electron 迁移路径也补上动态签名校验。

每个资料库持久保存一个公开 UUID 账号标识；仅在原生项目明确不存在时，使用旧路径解锁原来的 master key，再导入原生钥匙串并读回核验。已有钥匙不能被覆盖；取消、超时、错误或冲突均停止。`key-provider.json` 只有版本和账号 UUID，不保存密钥。原 `key-envelope` 保留且迁移前后 SHA-256 一致，原始聊天和资料库不重建。

### 实际验证

- 首次迁移成功，原资料库正常解密；只读 ACL 元数据确认新项目绑定独立 helper。
- 第一次签名：主应用 `3c33b49529db4e8204b2b65646237c77866870f9`；helper `9b5308ef38651a0928b016482e000f63bb309c53`。
- 修改主应用资源后重新打包：主应用变为 `8453fc65be76d1dd7a2c9e087c0bc97b6395dd9f`，helper 哈希不变。安装后约 1 秒载入原加密资料库，直接走原生钥匙读取。
- 新 Keychain 项目的 partition 正好是 `cdhash:9b5308ef38651a0928b016482e000f63bb309c53`，不是主应用的可变哈希。没有开放给所有应用，没有移除分区校验，也没有保存系统密码。

这证明本次普通应用资源更新可以复用授权。将来若辅助程序本身、签名证书或其签名资源改变，macOS 仍可能再次要求授权；登录钥匙串被锁定时也仍遵守系统验证。系统安全弹窗由用户本人完成，工具不能代填密码或绕过 SecurityAgent。

## 截图、OCR 与模型选择

独立窗口捕获现在使用实际 `pointPixelScale`，开启按输出尺寸缩放并保持比例，避免窗口只占截图左上角、其余区域变黑。截图和键鼠映射继续使用同一份 CGWindow 桌面矩形；切窗、移动、旧截图、停止均使旧动作失效。真实测试中的用户切窗/调整窗口确实触发暂停，未放松这条约束。[Apple scalesToFit](https://developer.apple.com/documentation/screencapturekit/scstreamconfiguration/scalestofit)。

OCR 使用原始分辨率，视觉模型使用有界预览。英文价格和模型标签增加独立识别；必要时对同一行作最多六个局部放大识别，再精确映回原图坐标。在真实菜单上，`Hy3` 与 `0.00x` 均得到 1.0 的识别置信度，归一化中心高度相差约 0.00073。

免费 Hy3 不再依赖“按钮必须在下半屏”的假设。每个任务需要截图中同一行的 Hy3 和零倍率证据，点击该文字框后再观察菜单关闭及当前选中标签；过期凭证、不同模型、错行价格、菜单未关闭均不能授权输入。重复识别框按物理位置合并。本地检查和发给模型的 OCR 内容分别有界，重要证据不会被长页面挤掉。

## 模型分工

用户明确指定：默认 `deepseek-v4.1-flash`，思考 `high`；简单会话保留免费 Hy3。Bunny 的截图规划 API 已明确发送 `reasoning_effort=high` 和 JSON 输出约束，实际测试约 2.25 秒返回有效 JSON、响应模型 ID 相符。当前账号目录返回 Flash 的倍率 `x0.11 credits`、支持图像和 reasoning，思考等级为 low/high/max、默认 high。倍率是本次目录快照，不作长期价格承诺。不自动换成 Pro 或其他付费型号。Bunny 的日常聊天智力配置由设置面板独立保存。

WorkBuddy GUI 的模型设置是另一条链路。本次真实会话的非内容元数据确认 `model=deepseek-v4.1-flash`，没有可独立核验的 effort 字段。5.9.2 源码具备将所选 effort 送入请求元数据的路径，但空的 GUI 模型默认值由其请求层决定，不能据此认定为 high。因此界面和规划提示明确区分：代理规划固定 high；WorkBuddy 对话强度以 WorkBuddy 自身设置为准，有明确可见控件时才设置。不会把 Bunny 的 API 参数冒充 GUI 会话参数。

## WorkBuddy 真实派发与完成监听

正式安装版 0.3.4 对 WorkBuddy 5.9.2 发出原文任务：“只回复‘workbunny协作验收通过’，不要调用任何工具，也不要修改任何文件。”同时附上微信只能视觉键鼠、不得支付/退出/使用微信系统工具的固定约束。此任务没有要求 WorkBuddy 执行复杂开发。

- 原生适配确认首页唯一编辑器、精确 Flash 标签、草稿原文一致，再点击发送一次。完整正文成功回读；相同的已准备草稿可幂等接续，不重复填入。
- 实际界面显示 WorkBuddy 助手回复 `workbunny协作验收通过`，并显示 `已完成 9s`；Bunny 从开始到进入待验收约 19.8 秒。这是单次简单任务样本，不代表复杂任务或长期稳定性的性能承诺。
- 现有 Monitor 从真实会话 `bcf0b2af-d420-4fb4-8fa3-98effc9246c9` 读到完成，`status=ok`、工具步骤 0，助手答复包含验收文字；该会话记录的实际模型为 `deepseek-v4.1-flash`。
- 对当前截图中助手区域的回复人工核验后，调用确认结果。没有仅凭“发送按钮被点击”或用户气泡就判定交付。

WorkBuddy 富文本编辑器的空 AXValue 实际包含 FEFF、换行和自身提示文案；普通空字符串判断会误报有草稿。空段落也会多序列化一个 FEFF。修复只接受已实测的空结构，以及空行对应单个 FEFF 的等价表示，非空正文仍须逐字一致。直接 AXSetValue 不适配这个富文本控件，已改为确认焦点后用普通键盘事件输入、回读校验，再通过发送控件提交。

## 产品边界与下一阶段

`concept.md`、系统角色提示、托盘及设置入口同步采用“小秘书”边界。面板改为“工作与日常”，分别显示 Bunny 当前代理操作与既有 Monitor 提供的 WorkBuddy 实际进度；输入辅助收起，保留一键暂停、窗口变化暂停和明确验收。持久化的是操作意图与回执，用于停止后不重放输入，不是另一套复杂任务执行引擎。

当前已经验收面板发出简单 WorkBuddy 任务、读取完成状态，以及微信文件传输助手视觉发送。普通语音聊天尚未自动路由到派发入口；自动续聊催办、复杂交付内容验收、其他智能体软件以及其他社交联系人仍需后续迭代。本次不宣称这些已经实现。

原生协议 12 项检查、DesktopService 集成、隐藏 Electron 面板流程、Keychain provider 与拒绝伪父进程、旧钥匙迁移客户端、SQLite 加密资料库检查通过。面板测试使用隔离数据和 stub，不当作真实 WorkBuddy/微信验收；上述桌面结果来自另行运行的正式安装版。
