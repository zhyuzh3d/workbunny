# 对话协议与显示、朗读边界

适用：所有大脑来源，2026-10-26。

## 本轮故障的证据与根因

最近真实聊天中出现多次与用户问题无关的 `1.1`。使用当时所选模型、相同最近八条历史及正式提示复现：泛 JSON 模式返回原始正文 `1.1`，completion_tokens=3。不是 TTS 误读、界面截断或程序取错版本号。相同条件取消泛 JSON 模式后正常回答；严格结构模式正常；把历史助手消息也包装为同一 chat 协议后，泛 JSON 模式亦恢复正常。

这里存在共用架构问题：

1. 历史保存的是自然语言，却直接作为 assistant 示例发送，与当轮要求的结构化输出协议不一致。
2. 泛 JSON 模式与“符合产品协议”被混为一谈。服务返回的 JSON 值即使可解析，也不一定是包含 kind/text 或 intent 的产品回复。
3. 回复门控为兼容旧纯文本保留了旁路，裸数字可以进入气泡、TTS 和记忆；异常历史又被后续上下文引用。
4. 设置测试仅检查接口是否返回任意文字，没有覆盖正式对话使用的协议。

这些是本机实测的触发条件；不将其泛化为服务商所有模型都必然存在同一服务端问题。

## 当前统一契约

- 所有服务商的历史 assistant 消息都在请求时包装为 `{kind:"chat",text:...}`；不修改或清除真实历史，不对某次聊天做特判。
- 输出只能是 chat、action、skip。支持严格 schema 的传输使用 schema；其他传输使用其支持的 JSON 模式，但必须经过相同本地校验。服务商能力差异不构成校验豁免。
- 完整回复结束并通过字段、类型、重复键、尾随内容和正文检查后，才发布 chat 正文。截断或非法输出不进入 TTS，不保存为正常助手回答，也不执行动作。
- action 只进入任务调度器；用户看到并听到的是调度器生成的自然语言状态。skip 没有显示与朗读正文。
- chat.text 必须是自然对话。程序 JSON、代码围栏、工具 XML、角色分隔符等不能作为聊天正文；合法角色动作标签被去除后，才进入显示和朗读。
- 气泡发布和 TTS 入队处另有相同正文检查。任务面板里的进度数据仍走独立类型通道。
- 连接测试使用正式提示、相同输出约束和校验器，成功返回 `protocolVerified:true`，而非把任意 HTTP 200/任意字符串视为通过。

正常算术回答 `chat.text="1.1"` 是有效对话；不建立数字或某个模型名的黑名单。

## 依据与验证

xAI 的[结构化输出文档](https://docs.x.ai/developers/model-capabilities/text/structured-outputs)说明了 json_schema 及对象字段约束；本地校验仍负责产品的完整协议与呈现规则。

隔离检查覆盖所有来源共用的 scalar/array/plaintext、重复键、未知字段、截断、跨分片尾随数据、空正文、嵌套程序数据、合法动作标签清理，以及正常数字表达。正式安装路径另行验证连接测试、真实 Grok 多轮对话与 action 的 UI/TTS 通道，不能用 API 探针替代实际应用验收。

边界：结构校验防止程序数据泄漏到对话，不证明回答事实正确；视觉识别和任务交付仍需各自证据核验。
