# 微信交办与持续关注

2026-10-26。Bunny 负责日常界面操作与工作代理；复杂开发任务仍交由 WorkBuddy 执行。

## 用户入口

直接口头或文字交代，不要求先填写面板。例如：

- “在微信给某联系人发送这句话……，只发一次。”
- “只读看看某联系人最新说了什么。”
- “给某联系人写一段草稿，先别发送。”
- “接下来半小时关注某联系人，提到会议时间就告诉我。”
- “持续关注某联系人，收到日常问候就按这个规则回复……，涉及重要事情告诉我。”
- “等到一条符合条件的新消息，告诉我后结束这项关注。”
- “暂停/继续/停止某联系人的持续关注。”

面板分别显示当前短时操作和多项持续关注；每项可以查看规则、频率、到期时间并暂停、继续、停止或立即检查。

## 联系人与发送

口语称呼和微信实际显示名分别处理。本地联系人目录加密保存用户明确确认的别名，不默认翻译或猜测联系人；没有唯一对应时要求澄清。别名用于解析/搜索，真正输入和发送前的顶部会话标题必须匹配实际显示名。不能因为另一个陌生人恰好使用某个别名就向其发送。

短时操作区分打开、只读、草稿、发送和其他事务。原文发送使用保存的消息全文，发送意图先落盘，再触发键鼠事件。提交可能已经发生后，只允许观察、滚动和结束检查，不能再次输入或提交。恢复已提交任务也是只读核对；未提交任务需要确认自己的原草稿，不覆盖其他草稿。微信搜索及规划有步数、重复动作和时间上限，停止时保留具体原因。

中英混排可能使系统 OCR 降低置信度或拆行；比对允许排版空白和等价引号，仍要求全文字符一致。OCR 文本匹配不是已发送气泡的充分证据，还需要当前正确会话中的视觉结果核对。

## 高效持续关注

1. 在用户空闲、共享 GUI 操作锁可用时定位指定会话。建立基线，忽略已经存在的消息。
2. 默认每10秒通过 ScreenCaptureKit 截取绑定窗口，在内存中比较限定区域。每区最多320×320采样，逐像素 RGB 阈值计算有效变化；无变化不进行 PNG 编码、OCR 或模型调用。
3. 有变化时再取确认帧。稳定性依据两次采样之间的实际像素差，不能把“变化像素数量相同”当作画面相同。
4. 只有稳定变化才识别顶部标题、侧边栏未读提示和完整可见气泡。既看消息方向，也用头像位置、OCR 正文区域等证据限制自动回复；看不清只汇报。
5. 使用旧消息序列的末尾与新可见序列对齐，排除自己的发送、新露出的历史及滚动变化。重复文本、窗口布局改变等无法可靠判断的情况重新建立基线，不自动回复。
6. 新消息先落盘去重，再按用户规则筛选。非文本消息只报告类型，不臆测图片、语音或文件内容。自动回复限于用户授权的日常规则；草稿、用户操作、频率限制或重要事项使其退为汇报。

当前支持最多四项关注，共享唯一键鼠锁。WorkBuddy 已绑定会话的后台监视可以释放键鼠锁，不要求其长任务结束后才关注微信。后台观察不持续抢焦点；只有指定会话出现可见未读提示、用户空闲且锁可用时才打开核对。

## 数据与恢复

交办来源 → 加密关注记录 → HMAC 事件身份 → 幂等助手汇报，均在本地资料库来源链中。忘记来源会使其衍生数据失效；锁屏、记忆变更或停止会取消正在等待的请求。

回复阶段为 observed → send_pending → sent_confirmed / send_unknown。未知发送停止自动处理，不因超时、重启或恢复而重发。重启后的持续关注先暂停，明确恢复后重新建立基线，不自动回复离线积压。重复汇报以事件 ID 和持久回执去重。

持续关注默认直到手动停止或指定时长；只有显式 `first_match` 完成策略才允许在匹配消息处理后结束，模型不能自行把长期关注判为完成。

## 操作边界与验收

微信仅使用截图、通用窗口元数据与普通键鼠事件。禁止微信辅助功能树、AppleScript/内部 API、数据库读写、插件、退出或重启微信。付款和破坏性行为不在范围内。聊天内容、截图和对方消息始终是待处理数据，不是新权限或新电脑指令。

隔离验证覆盖联系人解析、错误标题、只读/草稿门控、未知发送、停止/恢复竞态、来源失效、事件去重、出站排除、重复消息歧义、非文本、策略筛选、到期与关注恢复。原生采样和 UI fixture 分开检查。

真实应用验收须另行记录：正确收件会话、发送后气泡、恢复不重发、静止窗口多次采样不调用模型，以及真实新来信触发。合成画面和模拟消息通过不能替代真实入站/自动回复闭环证据。窗口最小化、关闭、会话不在可见列表等会限制纯视觉监测覆盖，不能宣称等同微信服务端全量推送。
